TP moro_maze - plan de trabajo paso a paso

Objetivo general
Implementar en un solo paquete ROS las 3 partes pedidas por el profesor:
1. Localisation
2. Global Planning
3. Local Planning / Control

Regla de trabajo
No avanzar al siguiente paso hasta que el actual funcione y quede probado.

- Permite probar cada bloque por separado.

Condicion para cerrar este paso:
Queda confirmada la arquitectura de 3 nodos y sus nombres.

Resultado esperado al cerrar:

- Los nombres finales son:
  - `localisation_node`
  - `global_planner_node`
  - `local_controller_node`
- Cada nodo tiene una responsabilidad unica y clara.

Test de Paso 1:
No es un test de ejecucion, es un test de consistencia de arquitectura.

Checklist:
1. Podemos explicar en una frase que hace cada nodo.
2. Ningun nodo mezcla las 3 responsabilidades a la vez.
3. La arquitectura cubre exactamente:
   - localizacion

Si esa checklist se cumple, Paso 1 queda cerrado.

Paso 2 - Definir interfaces ROS
Objetivo:
Dejar fijos los topics, mensajes y parametros principales.

Estado actual:
Aprobado y fijado para implementar.

Interfaces recomendadas:
- `localisation_node`
  - subs: `/scan`, `/map`
  - pubs: `/estimated_pose`, `/estimated_pose_cov`, opcional `/scan_raster`
- `global_planner_node`
  - subs: `/map`, `/estimated_pose`
  - pubs: `/global_path`
- `local_controller_node`
  - subs: `/map`, `/estimated_pose`, `/global_path`
  - pubs: `/cmd_vel`

Mensajes recomendados:
- `/estimated_pose`: `geometry_msgs/PoseStamped`
- `/estimated_pose_cov`: `geometry_msgs/PoseWithCovarianceStamped`
- `/global_path`: `nav_msgs/Path`
- `/cmd_vel`: `geometry_msgs/TwistStamped`
- `/scan_raster` opcional: `nav_msgs/OccupancyGrid`

Entradas ya verificadas en este mundo:
- `/scan`: `sensor_msgs/LaserScan`
- `/map`: `nav_msgs/OccupancyGrid`
- `/tf`: `tf2_msgs/TFMessage`
- `/odom`: `nav_msgs/Odometry`

Parametros iniciales sugeridos:
- `scan_topic`
- `map_topic`
- `pose_topic`
- `path_topic`
- `cmd_vel_topic`
- `use_sim_time`

Contrato ROS final acordado para este TP:
- `localisation_node`
  - subscribe `/scan` : `sensor_msgs/msg/LaserScan`
  - subscribe `/map` : `nav_msgs/msg/OccupancyGrid`
  - publish `/estimated_pose` : `geometry_msgs/msg/PoseStamped`
  - publish `/estimated_pose_cov` : `geometry_msgs/msg/PoseWithCovarianceStamped`
  - publish opcional `/scan_raster` : `nav_msgs/msg/OccupancyGrid`
- `global_planner_node`
  - subscribe `/map` : `nav_msgs/msg/OccupancyGrid`
  - subscribe `/estimated_pose` : `geometry_msgs/msg/PoseStamped`
  - publish `/global_path` : `nav_msgs/msg/Path`
- `local_controller_node`
  - subscribe `/map` : `nav_msgs/msg/OccupancyGrid`
  - subscribe `/estimated_pose` : `geometry_msgs/msg/PoseStamped`
  - subscribe `/global_path` : `nav_msgs/msg/Path`
  - publish `/cmd_vel` : `geometry_msgs/msg/TwistStamped`

Frames acordados:
- mapa global: `map`
- pose del robot para control/planner: expresada en `map`
- path global: expresado en `map`
- laser esperado desde simulacion: `base_scan`

Notas de implementacion acordadas:
- No usar `navigate_to_pose` de Nav2 como solucion del TP.
- No usar el planner/controlador de Nav2 como solucion final.
- Se permite usar `/map`, `/scan`, `/odom`, `/tf` como entradas del simulador.
- El path del planner propio debe publicarse en coordenadas mundo.

Condicion para cerrar este paso:
Queda escrito y acordado el contrato ROS de todo el sistema.

Test de Paso 2:
1. Confirmar tipos reales de entrada:
   - `ros2 topic info /scan`
   - `ros2 topic info /map`
   - `ros2 topic info /odom`
   - `ros2 topic info /cmd_vel`
2. Confirmar que el contrato final queda asi:
   - localizacion lee `scan + map`
   - planner lee `map + estimated_pose`
   - controller lee `map + estimated_pose + global_path`
   - controller publica `/cmd_vel` como `TwistStamped`
3. Si no hay dudas ni conflictos de tipos, Paso 2 queda cerrado.

Resultado de este paso:
Paso 2 aprobado.
